## P0-1 重审完成后 AI 终端仍展示旧审查结果

**画像**：核心玩家（Power User）— 对应 `t4_edit_editor.png → t4_edit_rereview_score80.png` 场景。

### 复现路径
1. 发布一个含 Java 代码块的帖子，等待 AI 审查完成（如首审 30 分，见 `t2_like_toggled_off.png`，头部与终端均为 30，一致）。
2. 点击 Edit，优化代码（补上除零守卫），保存并跳回详情页（`EditPostPage.tsx:119-120`）。
3. 后端将 `aiReviewed` 重置并重新触发审查（`VibePostServiceImpl.java:242-251`）。审查完成、页面轮询拿到新数据后，观察头部与终端。

### Expected vs Actual

| | 内容 |
|---|---|
| **Expected** | 头部 "AI Score" 与 AiReviewTerminal 内 Score 始终展示同一次审查结果；重审期间终端应显示进行中状态而非旧结果 |
| **Actual** | 头部显示 `AI Score: 80/100`，下方终端仍显示 `Score: 30/100 · MEDIUM · Needs Review`（`gui-test-screenshots/t4_edit_rereview_score80.png` 直接取证） |

### 证据
- `frontend/src/pages/PostDetailPage.tsx:100-104`：帖子查询在 `aiReviewed === 1` 时停止轮询——重审完成后帖子数据被重新拉取，头部 `post.aiReviewScore` 更新为新分 80。
- `frontend/src/pages/PostDetailPage.tsx:118-127`：审查详情查询 `['agent-logs', 'post', id, 'latest']` 设有 `staleTime: 1000 * 60 * 5`，且全文件未对该 queryKey 做任何 `invalidateQueries`。重审完成后它命中的是 **5 分钟内的旧缓存**，直接返回首审 30 分的旧结果。
- 矛盾的机制根源：头部走"帖子"缓存（已更新），终端走"审查详情"缓存（未失效），两条缓存生命周期不同步。
- 截图证据：`t4_edit_rereview_score80.png`（头部 80 / 终端 30 并存于同一屏）。

> 核心卖点是 AI 审查，用户优化代码后最关心的就是"分数变了没、建议变了没"，此时展示旧结论等于给出错误反馈。定级 P0。

## P1-2 点赞数字与高亮不同步（三重成因）

**画像**：破坏性用户（Chaos User）— 高频狂点场景（压测 `like_toggle.lua` 语义）。

### 复现路径
1. 打开任一帖子详情页，对 ♥ 按钮以每秒 5+ 次的频率连点 10 次。
2. 或：点赞 → 刷新页面 → 观察高亮；点赞 → 取消点赞 → 观察数字。
3. 对照 `t2_like_toggled_off.png`：截图中红心为**高亮填充**状态，计数却为 **0**（截图名为"已取消点赞"），高亮与数字已经背离（成因归属需实测确认，但代码层面三种成因均成立）。

### Expected vs Actual

| | 内容 |
|---|---|
| **Expected** | 高亮 = "我当前是否已赞"（服务端真值）；数字 = 该帖真实点赞数；狂点后两者收敛一致；未登录点击有明确反馈 |
| **Actual** | ① 刷新后高亮永远为灰色（即使我曾点赞）；② 取消点赞后数字可能跳回旧值；③ 狂点时本地 toggle 次数与服务端 toggle 次数不匹配，高亮与数字各自漂移；④ 未登录点击无任何反馈 |

### 证据（三重成因）

**成因 A：点赞状态从不回填。**
- `frontend/src/pages/PostDetailPage.tsx:89-90`：`liked` 恒初始化为 `false`，无任何从服务端回填的逻辑。
- 后端 `PostPageVo.java:23` 仅有 `likeCount` 字段，**没有 `likedByMe`**；`LikeCounterService.isLiked()` 已实现（`LikeCounterService.java:106`）但只被 `DemoShowcaseController.java:67` 使用，未接入帖子详情接口。

**成因 B：falsy 回退让取消点赞"复活"旧数字。**
- `PostDetailPage.tsx:383`：`{likeCount || post.likeCount}` —— 取消点赞后服务端返回 `currentLikes = 0`，`setLikeCount(0)` 后因 `0` 为 falsy，渲染回退到过期的 `post.likeCount`（如 5），数字凭空跳回。

**成因 C：狂点无锁 + 闭包陈旧值。**
- `PostDetailPage.tsx:143-149`：
  ```ts
  const handleLike = async () => {
    const res = await apiClient.post('/posts/' + id + '/like');
    setLiked(!liked);   // ← 读取闭包中的旧 liked，连点时多次读到同一个旧值
    setLikeCount(res.data.data?.currentLikes ?? likeCount + (liked ? -1 : 1));
  };
  ```
  无 `in-flight` 锁、无防抖、按钮无 `disabled`。而 `like_toggle.lua:10-18` 的语义是**每次请求都 toggle 一次**（SISMEMBER 反转），狂点 N 次 = 服务端真实 toggle N 次；前端 `setLiked(!liked)` 却可能因 React 批处理/陈旧闭包少翻若干次。乱序返回的 `currentLikes` 还会互相覆盖。两侧计数路径天然发散。

### 🔧 修复 Prompt（投喂 Fullstack-Dev）

```
修复点赞功能"数字与高亮不同步"的 P1 缺陷，共三处。

A. 服务端真值回填：
1. 后端 PostPageVo（src/main/java/com/nexus/campus/dto/PostPageVo.java）新增
   Boolean likedByMe 字段；帖子详情组装处调用已有的
   LikeCounterService.isLiked(postId, userId)（LikeCounterService.java:106）填充；
   未登录时填 false。注意保持接口向后兼容。
2. 前端 PostDetailPage.tsx：post 加载后用 post.likedByMe 初始化 liked state
   （替换 89 行的 useState(false)），并保留 likeCount 初始值取 post.likeCount。

B. falsy 回退：
3. PostDetailPage.tsx:383 的 {likeCount || post.likeCount} 改为
   {likeCount ?? post.likeCount}，并把 likeCount 初始值直接设为 post.likeCount
   （post 到位后 setLikeCount(post.likeCount)），使 0 能正常显示。

C. 狂点防抖与乐观一致性：
4. handleLike 增加 useRef<boolean> in-flight 锁：请求未返回前忽略后续点击；
   同时按钮在 in-flight 时不禁用视觉（保留手感）但拦截重复请求。
5. setLiked 使用函数式更新 setLiked(prev => !prev)，或更优：以服务端返回为准——
   让 /posts/{id}/like 响应体返回 { currentLikes, liked }（后端 Lua 返回 SCARD，
   liked 可由 LikeCounterService.isLiked 在 toggle 后回查），前端完全以响应渲染，
   彻底消除本地猜测。

- 补测试：a) PostPageVo 含 likedByMe 的序列化测试；b) 前端组件测试 mock 连续两次
  点击仅发出一次请求；c) 前端渲染 0 的边界测试。既有 226 项测试保持全绿。
```

## P1-3 未保存内容零留存守卫（刷新 / 切路由即全丢）

**画像**：破坏性用户（Chaos User）— DraftsPage 编辑时强制刷新、切换路由。

### 复现路径
1. 进入 `/post/new`，输入标题与大量正文，**不点** Save Draft。
2. 按 F5 强制刷新，或点击导航去往其他页面。
3. 返回 `/post/new`。

### Expected vs Actual

| | 内容 |
|---|---|
| **Expected** | 有未保存修改时：刷新触发浏览器离开确认（beforeunload）；切路由被拦截询问；或内容被自动保存到本地草稿，回来后可恢复 |
| **Actual** | 三者皆无，内容静默全丢。`DraftsPage.tsx:54` 的文案 "Local drafts saved in this browser" 只覆盖手动保存的草稿；`CreatePostPage.tsx` 中 `handleSaveDraft`（243-267 行）是唯一写入 `localStorage` 的入口 |
| **EditPostPage 更糟** | `EditPostPage.tsx` 连草稿机制都没有，仅 Cancel 按钮（231-237 行），刷新即丢且无任何提示 |

### 证据
- `CreatePostPage.tsx`：全文件无 `beforeunload`、无路由 blocker、无自动保存 effect；唯一的持久化在 `handleSaveDraft`（243-267 行）与提交成功后清除（313-319 行）。
- `EditPostPage.tsx`：同样无任何守卫；`Cancel`（231-237 行）直接 `navigate` 丢弃修改且无确认。
- `DraftsPage.tsx:23-34`：仅读取 `localStorage`，行为本身正确，但上游不自动落盘，列表必然缺失"未手动保存"的内容。

### 🔧 修复 Prompt（投喂 Fullstack-Dev）

```
为创帖与编辑流程补齐"未保存内容留存"三件套，P1。

范围：frontend/src/pages/CreatePostPage.tsx、frontend/src/pages/EditPostPage.tsx。

1. beforeunload 守卫（两页）：
   增加 useEffect，当存在未保存修改（当前表单值 ≠ 初始加载值，用一个
   isDirty 派生 state 计算，CreatePostPage 还需排除空表单）时注册
   beforeunload 监听并 e.preventDefault()（触发浏览器原生确认）；无修改时注销。

   项目使用 react-router-dom v6 的话使用 useBlocker/unstable_useBlocker
   （或升级至支持的版本），isDirty 时弹自定义确认框（沿用现有 Toast/Dialog 风格），
   确认后才放行。

3. CreatePostPage 自动草稿：

   autosave 恢复优先级必须高于 template scaffold。

4. EditPostPage 最小方案：
   仅做 1 + 2（编辑已有帖不宜写本地自动草稿，避免版本混淆），Cancel 按钮

- 编辑页修改后点 Cancel：出现确认框；确认后丢弃、取消后停留。
- 测试矩阵：beforeunload 触发/不触发两例；autosave 写入与提交后清除两例；
  恢复优先级（autosave > template）一例。既有测试全绿。
```
