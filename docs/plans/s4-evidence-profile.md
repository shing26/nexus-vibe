# S4 切片 spec — 证据档案（声誉即证据）

来源：[产品提案 v3](../product/community-proposal-review-in-public.md) 的 S4 切片，采纳记录 [ADR-0022](../adr/0022-reopening-scope-for-the-self-demonstrating-community.md)。
状态：**spec 草案（2026-11-16），待拆 ticket 后逐票冻结契约。**

## 目标

个人主页从"三项主格 + 一行次级文字"（设计 B 轮已落地）升级为可追溯的证据档案：
**AI 评分曲线**可见，**每个数字可点开到它来自的原始 `ai_review_log` 行**。
判据不是"统计更多"，而是"每条统计都能被追问到底"——这是 AGENTS.md 的 claims 纪律在产品面的落地。

## 数据可用性（写代码前先钉死，避免发明数据）

| 提案要求 | 现有数据 | 结论 |
| --- | --- | --- |
| AI 评分曲线 | `ai_review_log`（`selectLatestCodeReviewLogsByUserId`），`resultJson.score`，`createdAt` | **可做**：按帖子取最新一次 code review，画分-时间散点/折线 |
| 被评审过的帖子数 | 同上（去重 postId） | **可做**（B 轮已显示该数，S4 加可点开） |
| 每条数字 → 原始日志行 | `ai_review_log.id`；已有 `/agent-logs/post/{id}` 与 `/latest` | **可做**：profile 侧需要一个按用户聚合的"我的评审记录"读取面（见 S4-1） |
| 被采纳建议数 | 无"采纳"信号：`vibe_comment.sentiment` 是 **LLM 语气分类码**（0 未分类/分类枚举），不是社区投票 | **不可做**（需 S2 的投票列），本切片不做，spec 与提案同步更正 |
| 解决他人问题数 | 无"已解决"标志；该字段属 S2 schema | **不可做**，本切片不做 |
| 共裁参与度 | 同上：需要真正的社区投票，`sentiment` 列不能复用 | **不可做**，本切片不做 |

**对提案的更正**（本 spec 生效）：提案 S2 段写的"复用 sentiment 列"不成立——sentiment 是
语气分类结果，不是投票；S2 需要新增投票存储。S4 因此只交付上表"可做"三项，其余等 S2。

## 验收标准（草案，逐票细化后冻结）

1. profile 页有 AI 评分曲线：数据点 = 该用户每个被评审帖子的**最新一次** code review 分数与时间；
   无数据时显示空态（不下假点、不画零线）。
2. 曲线上每个点、以及"被评审过 N"这个数字，都能导航到对应帖子的评审记录视图
   （复用既有 `/agent-logs/post/{id}` 读取面，不新建重复端点；如需按用户聚合则在 S4-1 里明确）。
3. 统计与曲线的每个数字都标注来源（哪个表/哪次运行），实现"可追问"而非"看起来专业"。
4. 不动 schema；不新增运行时依赖；后端改动限于读取面与测试。
5. 未登录可见（公开档案）；不泄露其他用户的安全审核结论内容（只给分数/严重度/时间/链接）。
6. 测试：后端聚合查询的单测 + 前端曲线与跳转的组件测试；断言改动逐条留痕。

## 切片切分（tracer bullets，ticket 在 `docs/tickets/s4-*.md`）

| Ticket | 内容 | 依赖 |

| S4-1 | 读取面：按用户聚合的评审记录（帖子、时间、分数、严重度、日志 id），复用既有表；后端测试 | 无 |

每票走验收链路（契约冻结 → 独立实现 → 独立 Verifier → 书面签收）。

## Rejected

- **在 profile 造一套新的"声誉分"**：无法溯源到具体日志的合成分数正是本项目反对的东西。
- **复用 `sentiment` 冒充共裁数据**：语义不符（语气分类 ≠ 社区投票），会产生假指标。
- **把曲线做成装饰性 sparkline**：规范第 6 条"honest AI surfaces"——图形必须对应真实数据点与可点开的来源。
