# 0007 — A degraded dependency is not an unhealthy container

The container healthcheck polls `/actuator/health`, and until now that answer was Boot's aggregate of every registered indicator. Redis and Elasticsearch were two of them. The application does not need either to serve a user: the cache falls back to `type: simple`, the like counters keep working from MySQL, and search falls back to a SQL query. So a Redis blip moved a fully serving instance to `DOWN`, and a `DOWN` health answer makes Docker restart a process that was answering requests, which is how a two-second dependency hiccup becomes a minute of real outage plus an empty LLM-retry queue. This was measured rather than argued: the first version of `ActuatorMetricsTest` failed with 503 on `/actuator/health` in a context where the app was otherwise healthy and simply had no Redis or Elasticsearch to talk to.

We split health into two levels with a new status. `DEGRADED` means the dependency is unavailable and the main path still serves; the status order puts it below `unknown` and above `up`, and `management.endpoint.health.status.http-mapping.degraded` is explicitly 200 so an unmapped-status default can never turn it fatal again. `/actuator/health` therefore answers one word about servability, and servability is decided by real storage: `db` keeps its genuine `DOWN`, because without the database nothing works and a restart is the right response. Explanation moves to a named group, `/actuator/health/deps`, which carries `db`, `redis`, `elasticsearch` and the new `llm` component with details, reachable only inside `nexus-net` because nginx now 404s every actuator path except the exact health probe. The starter Redis and Elasticsearch indicators are switched off and replaced by ours under the same component names, since they report `DOWN` and cannot be remapped per component.

Alternatives rejected: folding degradation into the top-level status, which is the behavior being removed; leaving health alone and relying on metrics plus dashboards, since Docker acts on the healthcheck and not on Prometheus, so the outage would still kill the container before anyone read a graph; and probing a synthetic API request in the healthcheck instead, which would couple liveness to LLM availability and drop the storage signal that actually matters. Note that the alert rules and the `llm` gauge, not this endpoint, are how an operator learns what is degraded: `/actuator/health` returning 200 no longer means every dependency is present. Fail-closed is a separate idea and stays separate: it is what the safety path writes when the LLM is unreachable (ADR-0004), while `DEGRADED` is what the process says about itself.

## Amendment (2026-09-14): one status code was answering two different questions

This ADR mapped `DEGRADED` to HTTP 200 and pointed two consumers at one URL without noticing they ask different things. `Dockerfile:38` polls `/actuator/health` to decide whether to replace a container. `docker/nginx/nginx.conf` forwards the *public* `/actuator/health` to the same document, so an outside observer of the site was reading a container-lifecycle verdict. During a full LLM outage both answered 200: correct for Docker, and misleading for the one person whose actual question is "can users still use this site".

Health is now split by audience rather than only by detail level. The named group `servable` (`management.endpoint.health.group.servable`) contains `db` alone and answers the visitor question; the container healthcheck keeps the aggregate. nginx forwards the public URL onto `/actuator/health/servable`, so an existing external probe keeps its address and gets a strictly narrower answer: a status, no `components`, no `groups`, no dependency names. `HealthSemanticsIntegrationTest` pins that the servable group is `UP` while the top level reads `DEGRADED`; the drill pins the same distinction across the proxy (`public-health-answers-only-servability`) and adds the negative case (`app-death-is-not-reported-as-health`): stop the app and the public answer must stop being 200.

Alternatives rejected: 404ing the public health endpoint, which throws away the only outside view this deployment has; and a separate liveness endpoint, which answers "is the JVM awake", a question nobody is awake to act on for a single container with `restart: unless-stopped`.

The consequence worth stating plainly: the public 200 now means only "a user with a browser and a working database can use the site". Dependency truth lives at `/actuator/health/deps` inside `nexus-net` and in the alert rules, which is why the `noDataState` work in E3 belongs to this decision rather than sitting next to it. A narrower answer that nobody watches is worse than the honest confusion this replaced.
