# 0008 — Bootstrap administrator and an empty production seed

`DEMO_SEED_ENABLED=false` was supposed to mean "this is a real deployment", and in practice it meant two other things. `DataPreloader` still inserted the seven sample accounts, with a random password per boot: nobody could log in as them, but they held the usernames `admin`, `alice`, `bob`, they appeared on the leaderboard, and `init.sql` had already filled `vibe_post`, `vibe_comment`, `sys_message` and `ai_review_log` on the database's first start, so production shipped a feed of posts written by people who were never meant to exist. At the same time there was no way in: the admin panel, the audit log and the review queue all require the `ADMIN` role, and with seeding off nothing granted it, which left "install the app" ending in an operator pasting an `INSERT` into MySQL by hand and hoping the bcrypt hash they generated matched the application's encoder.

Seeding now decides everything downstream of it. With `DEMO_SEED_ENABLED=false` the user table gets only the functional `AiAgent(999)` row, and `init.sql` keeps schema plus reference data (channels, tags) — the tables that describe what the site *is*, not what it *looks like*. Sample content moved into `src/main/resources/db/mysql/demo-content.sql`, applied by `DemoContentSeeder` under the same flag, insert-only, and only while `vibe_post` is empty; the H2 dev profile keeps reading `data.sql`, so the local demo experience does not change. The way in is `BootstrapAdminInitializer`: when seeding is off, no `ADMIN` exists, and `BOOTSTRAP_ADMIN_PASSWORD` is set, it creates `admin` with that password and logs one warning telling the operator to rotate it. If the password is not set it warns and stays out of the way — an unreachable admin area is a configuration gap, not a reason to refuse to serve — and if the username `admin` is already taken by a registered user it refuses to take the row over rather than silently changing someone's role.

Two properties matter more than the mechanism. The runner is idempotent in the direction an operator expects: it acts only while no `ADMIN` exists, so rotating the password, demoting the bootstrap account, or restarting a hundred times never rewrites a row it did not create. And the failure to bootstrap is visible rather than fatal: startup prints the missing variable, `/actuator/health` stays `UP`, and the public site works. What this does not buy is recovery — the platform still has no mail and no self-service reset, so a lost bootstrap password is fixed by an operator with database access, which is exactly the case the pre-deployment checklist now records.

Alternatives rejected: keeping the random-password ghost accounts, since "cannot log in" is not the same as "does not exist" and they kept being referenced by seeded content; making the first registered user the administrator, which turns a public sign-up race into privilege and cannot be reasoned about after the fact; and documenting a hand-written `INSERT` with a precomputed bcrypt hash, which works once, is wrong after any column change, and gives the operator nothing to see if it fails.
