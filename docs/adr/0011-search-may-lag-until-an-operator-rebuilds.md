# 0011 — Search may lag until an operator rebuilds, and the rebuild is the price

Search has two paths. When Elasticsearch answers, `PostSearchService` runs a `multi_match` over a CJK-analysed index. When it does not, `VibePostServiceImpl.searchPosts` falls back to a MySQL `LIKE` over title and content. Indexing is best-effort: `indexPost` is called on create and again on approve, logs one warning if the request fails, and nothing retries it. That left one question open, and the ticket that asked it (SEARCH-1) named two candidates: sweep the drift on a schedule, or accept a lag and say so.

What the failure actually looks like was unknown, so it was measured on 2026-09-17 in the `nexus-drill` project against the shipped image `nexus-vibe-app:20260916-05`, with two published posts carrying unique markers. The method, the endpoints every number came from, and what the run cannot prove are in
[es-index-lag-2026-09.md](../research/es-index-lag-2026-09.md).

| Moment | ES | search for the older post | search for the newer post | docs in the index |
| --- | --- | --- | --- | --- |
| older post published | up | 1 | — | 1 |
| newer post published **and approved** | down | 1 (MySQL path) | 1 (MySQL path) | 1 |
| ES restarted, healthy again | up | 1 | **0** | 1 |
| full rebuild via `/api/v1/admin/search/reindex` | up | 1 | 1 | 3 |

The row that decides this: **search returns more while the dependency is broken than it does after the dependency recovers.** Both posts were findable during the outage, because the MySQL path is a substring match with no index to be missing from. Once Elasticsearch answered again the query went back to the index, which had never received the newer post, and that post disappeared from search while continuing to exist, to be published, and to be reachable by direct URL.

A second run showed the same mechanism without an outage in it. The app was restarted with Elasticsearch stopped, logged `search degraded to MySQL`, and then had Elasticsearch come back. A post created and approved after the recovery was **not** indexed: the index count stayed at 3. `PostSearchService.esAvailable` is assigned once in `@PostConstruct` and read for the life of the process, so an app that starts without Elasticsearch never indexes another document, and nothing after the boot line says so. `ElasticsearchHealthIndicator`'s own comment already calls that flag unfit for reporting state, and it is right; the health endpoint probes for real, while the search and indexing paths still trust the constructor.

We accept the lag. Search may quietly stop being full-text, posts written and approved entirely inside an Elasticsearch outage stay out of full-text search, and the sanctioned remedy is the full rebuild that `restore.md` section 7 already scripts and has already been run against a real cluster (`{"requested":32,"reindexed":32,"failed":0,"complete":true}`, and the fail-closed counterpart when the cluster dies mid-run). Who runs it and when is now written in that section, which is what "accepted" has to mean: a policy nobody has been assigned is not a policy.

Alternatives rejected. A scheduled drift sweep, which is the candidate the ticket named: it needs a watermark the index does not carry (`buildPostDocument` writes `createTime` and no `update_time`, so the mapping and the whole index would change first), it adds a scheduled task and its tests, and it would not have fixed the case above — while `esAvailable` reads false, `bulkIndex` answers `refused`, so the sweep would report failures rather than repairs. A timer-driven full rebuild: it hides the drift signal, pays a whole index pass, and on this single node competes with live writes for the same heap. Re-indexing on a search miss: it turns a read into a write, and it cannot tell a genuine zero-result query from a missing document, so every keyword that legitimately matches nothing would trigger one. And leaving the behaviour as it is while calling it correct, which is the option the table above rules out: the reader-visible effect runs backwards.

The cost, stated plainly. Search can be missing recent posts with nothing in the response saying so. Every search during an outage pays the client's connect timeout first — measured at **2.11s** for a request that then answers 200 from MySQL. And if Elasticsearch is absent when the app boots, the index is abandoned for the life of that process. That last one is a defect rather than a policy choice: it turns a bounded outage into an unbounded silence, and a sweep would not have fixed it either. It is named here so the next round starts from the right sentence, and it is out of scope for a ticket that is a decision before it is code (ADR-0009).

One clause of the ticket is deliberately left undone, and it is better to say so than to leave it as an unchecked box. SEARCH-1 asked that, if the lag is accepted, "the search endpoint explains an empty result rather than returning a bare empty list". That clause was written against the assumption that the failure looks like a search coming back empty; the table above says the failure is the opposite one — during the outage nothing is missing, and the empty answer arrives *after* Elasticsearch recovers, for a post a substring query finds in the same database. It would also need a signal no component currently holds: `ElasticsearchHealthIndicator` probes liveness on purpose, the index carries no `update_time`, and nothing compares the index against MySQL, which is exactly why the breach this ADR describes is invisible until a reader reports it. The honest versions of "explain" are therefore either a new machine-readable response field, which reopens the contract round that settled on the HTTP status being the only story, or a per-query MySQL probe, which is the read half of the re-index-on-search-miss rejected above. Both are tickets, and a decision round is not where they get invented.
