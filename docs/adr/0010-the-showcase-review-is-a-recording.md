# 0010 — The showcase review is a recording of one real run

The strongest thing this repository has is not the forum around the pipeline. It is that an LLM review fails closed when the model is unreachable, repairs malformed output instead of publishing it, and writes a score back onto the post — and that behaviour was observable only by registering, publishing a post containing a code block, and waiting. Every other piece of evidence (the drill report, the load test, the ADRs) is behind a login or behind git. With `DEMO_SEED_ENABLED=false` in production there was no curated example either, so a stranger arriving at the landing page saw an empty forum and had no reason to believe the claim.

Two things follow, and they are different decisions. **The first is that the landing page points at one already-reviewed post**, gated on `campus.showcase.post-id` being set: `GET /api/v1/showcase` returns that post's id, title and score, and `ShowcaseEntry` links to it. Unconfigured deployments answer `data: null` and the component renders nothing, so a deployment that does not set the variable is byte-for-byte the deployment that existed before this. This is deliberately not `DEMO_SEED_ENABLED`: that switch means "fill the site with sample users and content", and turning it on in production would recreate the ghost-author problem ADR-0008 removed. This writes one post, by an account that already exists, and only when asked.

**The second is that the review shown is a recording rather than text that resembles one.** The snippet was published once through the ordinary publish path against the deployed stack; the pipeline wrote back the review comment and the `ai_review_log` row; both were copied out verbatim into `src/main/resources/showcase/` and are what the seeder inserts. Score and severity are parsed out of the recorded JSON rather than declared next to it.

That second decision is not fastidiousness. The first implementation hand-wrote both artifacts, and the page it shipped rendered **three empty sections** under Code Quality, Security and Suggestions. The hand-written row used `quality` / `security` / `suggestions`; the reader is `AiReviewDetailService`, which reads `codeQuality` / `securityConcerns` / `optimizationSuggestions`. Both are valid JSON, so nothing threw. No test failed, because the only test asserted that the fixture looked like the formatter's output — the fixture was being compared against its own author's memory of the schema. The page's entire reason for existing is a reader being persuaded by evidence, and it was showing four headings and a score bar over nothing.

Copying the real row is what makes that class of mistake unavailable rather than merely fixed: the field names cannot be wrong, because nobody typed them.

What this page proves is therefore bounded, and the seeded post says so in its own body: **it shows what the pipeline emitted for this snippet at the time it was recorded; it does not show that the model is reachable now.** A card that claimed "every field came out of the live pipeline" was the earlier revision's wording and was false — the fields came out of a stored row. The wording now says "a recorded run" and a frontend test fails if the phrase `live pipeline` returns.

Rejected alternatives:

- **Re-running the review at each startup.** This makes the most prominent page in the product fail whenever the LLM is down, which is precisely the condition the rest of the system is built to survive, and it spends a model call per restart. It also turns a deterministic page into a different page every deploy.
- **Keeping the hand-written fixture and fixing the field names.** It would have passed. It also leaves the page asserting a claim nobody can reproduce, in a repository whose whole discipline is that a claim without a reproducible path does not go in. The failure above is exactly what that discipline is supposed to catch, and it caught it late because the fixture was prose rather than evidence.
- **Making the landing page an unlisted `DEMO_SEED_ENABLED` deployment.** Two switches that both mean "write sample data" would drift, and ADR-0008 exists specifically to keep production free of seeded accounts.

The cost is a manual step that has to be documented rather than discovered: re-recording means publishing the snippet again, copying the comment and the `result_json` column into the two resources, and deleting the three seeded rows so the insert-only seeder writes them again — it never updates a row it did not create, so a reviewer who edits the showcase post keeps their edit. `scratch/record-showcase-review.py` is the throwaway that drove the publication, and it is deliberately not in the repository.

Two consequences worth stating plainly. First, the review on the page is a `deepseek-v4-flash` run from 2026-09-16 at severity `high` and score 3/10; a reader who re-runs the snippet today may get a different number, and that is the product working rather than the page lying. Second, the seeded rows live in MySQL with fixed ids, so this is row data and not a fixture the application switches to at runtime — there is no code path in which the application believes it is running a demo.
