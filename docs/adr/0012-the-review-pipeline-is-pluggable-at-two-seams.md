# 0012 — The review pipeline is pluggable at two seams, and only two

This project's subject is treating an LLM as an unreliable dependency, and the code that carries that claim lives in `agent/`: 11 files, 1,656 lines, plus a reconciliation task. Anyone reusing the repository therefore meets the pipeline first. What they cannot do is change it, because the two things a different forum would actually want to change are welded into core.

The trigger rule is "posts containing fenced code blocks", and it is written three times with three different wordings. The real gate is in `AiReviewEventListener` (`detectCodeBlocks(content).isEmpty()`); a second, differently-worded copy sits in `VibePostServiceImpl.updatePost` (which additionally excludes `postType=prompt`); and the publisher gates both events on a flag that has nothing to do with the rule. The reviewer is `AiReviewService`, 477 lines, which calls the model *and* writes the comment, the score and the log row in one method. A fork that wants a recipe forum to review posts with a photo, or no forum to review anything, edits files in two different packages and hopes it found every copy. That is not a boundary; it is a coincidence of where the code happens to sit.

The schema is further along than the code. `ai_review_log.reviewer` exists, and the two writers stamp `code-review-agent` and `safety-check-agent` into it, while three mapper queries filter on the literal `'code-review-agent'` to find a post's review. So the identity of the thing that produced a verdict is already persisted and already load-bearing — but as five hard-coded strings rather than as something a replacement could own.

Decision: publish exactly two seams, and keep everything the seams are not.

**`ReviewPolicy` decides whether a post is subject to review.** One method, answering that question from the post's content and type. The default implementation is today's fenced-block rule, unchanged. The trigger rule then exists in one place, and a fork asks it from both call sites instead of editing either.

**`Reviewer` produces a verdict.** Given a post that has already been claimed, it returns structured data: score, severity, the review body, and the identity to stamp into `ai_review_log.reviewer`. The default implementation is today's LLM path, including JSON repair. Recording the verdict — writing the comment, the score column and the log row — stays in core, because "what a verdict must satisfy before it may be recorded" is the project's argument, not a fork's choice.

Both are Spring beans resolved with `@ConditionalOnMissingBean`, so a fork replaces them by defining its own. Alongside the seams, one behaviour is corrected: `campus.ai.review.enabled=false` currently disables the LLM safety check as well, because the publisher gates both events on that one flag. The two switches exist and are not independent. Each event gets its own gate.

What stays fixed, deliberately, and is not a configuration item: the lease claim (ADR-0005), the reconciliation task, fail-closed (ADR-0004), the terminal notification when attempts run out, and review validity — the semantic check that decides whether a model's output is usable at all. These are the thesis. A pipeline that let a fork switch off its own failure handling would let it delete the reason this repository exists, and the ADRs would stop describing the code.

Alternatives rejected. Making `LlmClient` an interface: the circuit breaker, the per-address fallback, the JSON repair and the prompt isolation are implementation, not policy, and the interesting parts would remain *outside* any interface drawn there — it would add a forwarding layer with one implementation and no second caller. Making fail-closed or the lease configurable: same argument as above, and worse, because those are the parts a reviewer is being asked to trust. Removing the AI at the data-model level — nullable `ai_reviewed` / `ai_review_score`, conditional API surface, the fifteen frontend files that mention a review — because the runtime already supports a forum with no review at all through the flag, and `idx_post_ai_sort` is used by the AI-sorted feeds, so the work would change a contract to buy nothing a fork needs. A `ServiceLoader` SPI instead of Spring beans: this is an application, not a library, and the extra file-format ceremony buys nothing over a bean definition. And making the four-class safety taxonomy a seam in this round: those classes are persisted in `ai_review_log` and drive status transitions, so changing them changes data that already exists; it is named here so the next round starts from the right sentence rather than rediscovering it.

The cost, stated plainly. Two interfaces, two default implementations, the wiring, a set of tests proving that a replaced bean is the one that runs, and the documentation that makes the boundary findable — the four tickets in [ai-review-seam.md](../tickets/ai-review-seam.md). The risk is concentrated in one place: splitting `AiReviewService` moves persistence out from under the validity rules, and those rules are the tested part. If the split makes them harder to test, the split is wrong.

Why this is worth reopening a frozen scope (ADR-0009) for: the artifact claims it handles an unreliable dependency rather than merely calling one. A boundary someone else can replace without reading the 477-line class is the difference between a claim and a demonstration, and it is the one change that makes the reuse question answerable by the repository instead of by a conversation.
